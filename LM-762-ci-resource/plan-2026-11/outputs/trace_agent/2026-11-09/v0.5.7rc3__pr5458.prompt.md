## Step-by-step procedure

Do the steps in order. After each step, write 1–3 lines: **what you saw → what it means**.

### Step 0 — Which checks failed, and at which step?

- List the failed checks. Note which **passed**: e.g. K3 unit green but GH `test:` red is a strong clue.
- For each failed job, find the **failing step**.

| Fails at | Likely class | Go to |
|---|---|---|
| Set up job / Checkout / download / docker pull / `curl 5xx` / "runner lost communication" | **Infra** | Step 3, then Step 8 option R |
| Lint / pre-commit / mypy | **Code quality**: usually the PR's own code | Step 2, then report |
| Inside pytest / test script | **Test failure** | Step 1 |

### Step 1 — Read the end of the log and group the errors

- Find `short test summary info`, the final `N failed, M passed`, and `##[error]`.
- Group them:
  `grep '^FAILED' log | sed 's/::.*//' | sort | uniq -c` (by file)
  `grep '^FAILED' log | sed 's/.* - //' | sort | uniq -c` (by error type)
- Check for **hidden failures**: `--maxfail=1` / `-x` / "stopping after 1 failures" means more tests may be broken. pytest also shows only the **first error per test**, so fixing it may reveal more layers.
- Classify the error shape:

| Error shape | Usually means |
|---|---|
| `unexpected keyword argument`, `has no attribute` on a fake/`SimpleNamespace`, `ImportError` of a renamed symbol | **Test is older than the code** (API drift) |
| Message about kernel / `/proc` / sysctl / GPU / PATH / network / permissions | **Test depends on the host environment** |
| Assertion on values, wrong result | **Real logic bug** (PR or `dev`) |
| Timeout, hang, intermittent | **Flaky**: check history before blaming code |

### Step 2 — Is it related to this PR?

- `gh pr diff <N> --name-only`: does the PR touch the failing test, the code under test, or its imports?
- **Yes**: likely the PR's own bug. Go to Step 6 (reproduce), then Step 8.
- **No**: suspect **`dev` is red** or **the environment**. Go to Step 3.

### Step 3 — Do other PRs fail the same way at the same time?

- List runs of the same workflow (or Buildkite pipeline) from about 1 h before the first failure to now.
- Open 2–3 other failed runs and check for the **same test and error**. Do not count failures you did not open.
- Many unrelated PRs fail the same way → **`dev` is broken** (PR CI runs on the merge ref with `dev`).
- A sibling run minutes later passes the same job → **transient infra or flaky**.
- Only this PR fails, PR unrelated → **environment or agent-specific** (compare agents and queues).

### Step 4 — Find the change that caused it

- On `dev`, find recent merges that touch the failing path:
  `git log --since=<first_fail - 1 day> --oneline origin/dev -- <failing test dir> <code under test>`
- For API-drift errors, find who changed the symbol: `git log -S "<old_or_new_name>" -- <path>`.
- Build a **timeline** table: date, PR, what changed. Example from #6279:
  `09-21 PR X last CI green` → `10-20 #5911 merged` → `10-24 #5150 merged` → `11-04 PR X merged without rerun → dev red`.

### Step 5 — Why didn't CI catch it earlier?

Always answer this. It decides the prevention option. Check:

| Gap | How to check |
|---|---|
| PR merged on a **stale base** (semantic merge conflict) | last CI date of the culprit PR vs merge date; `compare` → `behind_by` |
| Test **skipped** in one pipeline | `importorskip`, markers; K3 unit `run.sh` installs **no vLLM**, so vLLM-gated tests run only in GH `test.yml` |
| Workflow does **not run on `dev` push** | `on:` block of `.github/workflows/test.yml` (as of 2026-11: `pull_request`, `workflow_call`, `workflow_dispatch`, no `push`) |
| Test reads **host state** that differs between agents | grep the code path for `/proc`, `os.environ`, `shutil.which`, GPU queries; compare with the fixture's mocks |
| Fail-fast flags hid failures | `--maxfail`, `-x` in `run.sh` / workflow |

### Step 6 — Reproduce (or say why you could not)

- Check out the exact commit (PR merge ref or `dev` SHA), install the **same extras as the pipeline** (e.g. `pip install vllm` for GH `test.yml`), and run only the failing tests.
- For env-dependent tests, fake the condition. For example, point a path constant to a temp file with the CI value instead of changing the host.
- If you cannot run it (no GPU, OS mismatch), say so and rely on log evidence.

### Step 7 — Is there already a fix?

Only now look for one:
- `gh pr list -R LMCache/LMCache --state all --search "<test name or error text>"`
- `git log origin/dev --oneline -- <failing path>` after the first failure time.
- If a fix is **merged**: the answer is "rebase on `dev`". Confirm the fix commit is not in the PR's merge base. Then compare your trace with the fix: same location? same reasoning?
- If a fix is **open**: link it and say what is left.
- If **none**: go to Step 8 and propose options.

### Step 8 — Options and recommendation

Score each option on **time to green**, **risk**, **blast radius**, **owner**.

| Option | Use when |
|---|---|
| **R. Rerun** | Infra/transient (5xx, runner lost, checkout fail). If seen ≥3×/week, also open an infra ticket. |
| **A. Revert culprit commit** | `dev` red and blocking many PRs, no quick fix |
| **B. Fix the test** (mocks, fakes, updated API usage) | Test is stale or host-dependent (#6350, #6279) |
| **C. Fix production code** | Test is right, code is wrong |
| **D. Change CI environment** | Agent misconfigured vs documented requirements. Do not use it to hide a test bug. |
| **Q. Quarantine** (`skip`/`xfail` + ticket + removal date) | Need green now, real fix needs more time |
| **G. CI guard** (always add one) | Require up-to-date branch / merge queue; add `push: dev` or nightly run; mock host state in fixtures; avoid `-x` hiding failures |

Decision rules:
- `dev` red and many PRs blocked: **A or Q first** (minutes), then **B/C** (hours), then **G**.
- One PR red because of the environment: **B**, not D.
- Infra: **R**, and track how often it happens.

### Step 9 — Impact (when `dev` was red)

- Red window: culprit merge time → fix merge time (or "still red").
- Number of PRs whose runs failed with the **same** error (only count ones you opened).

## Quick triage checklist (run before deep reading)

1. Fail **before** the test step? → infra, rerun, count recurrences.
2. Many **unrelated** PRs red with the same error in the same window? → `dev` red, look at recent merges.
3. Error mentions **host state** (kernel, `/proc`, GPU, PATH, network)? → env-dependent test.
4. Error is **API shape** (`unexpected keyword`, `no attribute`)? → stale test vs code drift, use `git log -S`.
5. One pipeline green, another red for the same tests? → compare install extras and skip conditions.
